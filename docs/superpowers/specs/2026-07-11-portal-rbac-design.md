# Ролевой доступ в клиентском портале — дизайн

**Дата:** 2026-07-11
**Проект:** ITL OrderFlow (`itl-orderflow`)
**Статус:** утверждено, готово к планированию реализации

## Проблема

Сейчас клиентский портал использует один общий `Client.portalToken` на всю компанию-клиента. Любой, кто получил эту ссылку, видит всё: проекты, коммерческие предложения, счета, тикеты. У клиента при этом уже есть несколько контактов с разными должностями (`ClientContact.position`), но эта модель никак не участвует в авторизации портала — это просто CRM-справочник.

Нужно, чтобы разные сотрудники клиента видели разные разделы портала в зависимости от роли: владелец — всё, бухгалтер — только финансы, операционник — только проекты и т.д.

## Подход

Переносим портальный доступ с уровня `Client` на уровень `ClientContact`. У каждого контакта — свой токен входа и своя матрица прав (набор чекбоксов по разделам портала). Права выставляются вручную для каждого контакта (гибкая матрица, не фиксированные роли-пресеты), с кнопкой быстрого пресета «Полный доступ» для контактов-владельцев.

Детализация — на уровне разделов портала, не на уровне отдельных заказов/проектов: контакт с правом «Проекты» видит все проекты своего клиента, а не только избранные. Привязка контакт↔конкретный заказ — не в скопе.

## Модель данных

Изменения в `prisma/schema.prisma`:

**`ClientContact`** — добавить поля:
```prisma
portalEnabled      Boolean  @default(false)
portalToken        String?  @unique

canViewProjects     Boolean @default(false)
canViewProposals    Boolean @default(false)
canViewFinance      Boolean @default(false)  // счета + платежи
canViewDocuments    Boolean @default(false)  // договоры, ТЗ, допсоглашения, акты сверки
canViewTickets      Boolean @default(false)  // просмотр + создание обращений
```
Плюс индекс `@@index([portalToken])`, как сейчас у `Client.portalToken`.

**`Client`** — удалить поля `portalToken`, `portalEnabled`. Единая точка входа в портал теперь — только через контакт.

По умолчанию у нового контакта все 5 прав выключены (безопасный дефолт) — админ включает нужные разделы явно при выдаче доступа.

### Миграция существующих данных

Отдельный скрипт миграции (запускается один раз при выкатке):
1. Для каждого `Client`, у которого сейчас `portalEnabled = true` и есть `portalToken`:
   - берём его `isPrimary` контакт, если есть; если контактов нет — создаём контакт-заглушку («Владелец», без email/телефона, если их нет в данных);
   - выставляем этому контакту `portalEnabled = true`, все 5 прав `true`, генерируем новый `portalToken` (`crypto.randomBytes(32).toString("hex")`, как сейчас).
2. После миграции колонки `Client.portalToken` / `Client.portalEnabled` удаляются.
3. **Организационный шаг вне кода**: старые ссылки/токены клиентов перестанут работать после деплоя — нужно будет разослать реальным клиентам новые персональные ссылки на контакт-владельца. Это должно быть учтено в плане релиза, не автоматизируется кодом.

## Аутентификация и сессия портала

- `/portal/login` ищет введённый токен в `ClientContact.portalToken` (вместо `Client.portalToken`), проверяет `contact.portalEnabled === true` и `client.isArchived === false`.
- Cookie остаётся `portal_token` (меняется только смысл значения — теперь это токен контакта), чтобы не трогать формат/имя cookie без необходимости.
- Новый серверный хелпер `requirePortalSession(permission?: PortalPermission)` в `src/lib/portal-session.ts` (или `src/actions/portal.ts`):
  - читает cookie, резолвит контакт + клиента + права одним запросом;
  - если сессии нет — `redirect("/portal/login")`;
  - если передан `permission` и у контакта его нет — `redirect("/portal?denied=1")`;
  - возвращает `{ contact, client, permissions }`.
  Используется в начале каждой страницы `(portal)/portal/**/page.tsx` вместо повторяющегося блока `cookies() → getPortalClient → redirect`, который сейчас продублирован в каждом файле.
- `(portal)/layout.tsx`: пункты меню (Проекты / Предложения / Счета / Документы / Обращения) рендерятся только если у контакта есть соответствующее право. В хедере показываем имя контакта и его `position` под именем компании.
- Если у контакта `portalEnabled = true`, но все права выключены — вместо пустого дашборда показываем экран-заглушку «Доступ не настроен, обратитесь к вашему менеджеру».

## Админ-часть: управление доступом

Текущая карточка «Доступ в портал» (`src/components/clients/portal-access.tsx`, привязана к `Client.portalToken`) удаляется. Управление доступом переносится во вкладку **Контакты** клиента — на каждый контакт (в `edit-contact-dialog.tsx` или отдельный блок в строке списка) добавляется секция «Портал»:

- тумблер «Доступ включён» (`portalEnabled`);
- 5 чекбоксов прав (Проекты / Предложения / Счета / Документы / Обращения);
- кнопка-пресет «Полный доступ» — проставляет все 5 чекбоксов (для контактов-владельцев);
- кнопка «Сгенерировать / перегенерировать токен» + копирование токена и ссылки на `/portal/login` (тот же UX, что в текущем `PortalAccess`);
- кнопка «Отозвать доступ» — гасит `portalEnabled`, не удаляя контакт и не стирая права (чтобы включить обратно одним кликом).

Server actions в `src/actions/portal.ts`:
- `getPortalClient(token)` → переименовать/заменить на `getPortalSession(token)`, резолвящий контакт + клиента + права;
- `generatePortalToken(clientId)` → `generateContactPortalToken(contactId)`;
- новый `updateContactPortalPermissions(contactId, { portalEnabled, canViewProjects, canViewProposals, canViewFinance, canViewDocuments, canViewTickets })`;
- новый `revokeContactPortalAccess(contactId)` (алиас на `updateContactPortalPermissions` с `portalEnabled: false`).

## Страницы портала

- `/portal` (дашборд): рендерит только те плитки/секции, на которые есть право. Бухгалтер видит только финансовую сводку, операционник — только сводку по проектам, и т.д. `getPortalDashboard` дозапрашивает только нужные для доступных разделов данные (не тянет заказы, если `canViewProjects = false`).
- `/portal/orders/[id]` — требует `canViewProjects`.
- `/portal/proposals`, `/portal/proposals/[id]` — требует `canViewProposals`.
- `/portal/invoices` — требует `canViewFinance`.
- `/portal/tickets`, `/portal/tickets/[id]`, `/portal/tickets/new` — требует `canViewTickets` (создание тикета — то же право, отдельного права на запись нет).
- **Новый раздел `/portal/documents`** — требует `canViewDocuments`. Список договоров (`Contract`), техзаданий (`TechSpec`), допсоглашений (`Amendment`) и актов сверки (`Reconciliation`) клиента в одной таблице (или табах), по аналогии с `/portal/invoices`: номер, тип, дата, статус, кнопка «Скачать PDF» (`generatedPdfUrl`). Детальные редакторы секций (`ContractSection`/`TechSpecSection` с Json-контентом) в портал не выносятся — это внутренний конструктор документов в админке, клиенту нужен только готовый PDF.

## Вне скопа

- Привязка контакта к конкретным заказам/проектам (доступ только к «своим» заказам) — детализация только на уровне разделов.
- Отдельные права на действия (например, «может создавать тикеты», но не видеть чужие) — одно право на раздел = просмотр + доступные в разделе действия.
- Email/пароль вместо токена — сохраняем модель персональных токен-ссылок, как сейчас, просто на уровне контакта, а не клиента.
